# Accessibility review: Phase 2c (light/dark switch)

Date: 2026-10-21. Scope: all seven pages, both themes. Standard: WCAG 2.2 AA.
Method: the automated gate (axe-core in Chromium at 320, 768 and 1280px, static
lint, pixel contrast, form-control boundary contrast, behaviour, motion and
rhythm tests) run once per theme, plus Chromium emulation of forced colours and
print. Results below are observations from this run; anything marked "not
performed" was not exercised by a person.

## What this phase added

A light/dark switch. Light stays the default look; dark is a second token set in
`content/theme.json`, generated into `assets/theme.css`. The visitor's system
preference is the default until they choose; the choice is remembered. No
visible copy was reworded, no link changed and no form field changed. Forms,
server verification and the content security policy are untouched.

- A `<button>` named "Dark mode" with `aria-pressed`, in the top bar and in the
  mobile menu. Decorative icon (moon while off, sun while on), 44px target,
  visible focus ring, keyboard operable, focus stays on it after use.
- `color-scheme` is set per theme so native controls, scrollbars and form
  placeholders follow.
- Fixed colours became theme-driven: the logo mark, the iris canvas, the select
  arrow, the Turnstile widget theme. Photographs are dimmed slightly in dark.
- Print always prints the light look and never prints the switch.

## How the mechanism works (what the tests rely on)

- Storage key `ayin-theme`, values `light` or `dark`, every access inside
  try/catch. Anything else stored is ignored.
- A small inline script in `<head>`, before the stylesheet link, sets
  `html[data-theme]` from the stored choice or the system preference. It is the
  only new inline script.
- Without JavaScript there is no `data-theme`: a CSS media rule scoped to
  `:root:not([data-theme])` gives a dark system the dark look, and the switch is
  hidden (it could not work).
- With nothing stored, the page follows system changes live. A stored choice is
  never overridden by a system change.

## What was tested in both themes

Every browser test that checks appearance is parametrised over light and dark,
rendering the page the way a visitor gets it (system scheme emulated and the
choice stored; the test asserts `html[data-theme]` first):

- axe-core at 320, 768 and 1280px on all seven pages: zero violations in both.
- Needs-review items: each is justified in `tests/a11y_review.json` and backed
  by a pixel measurement of the rendered glyphs, in each theme the entry covers.
- Pixel contrast review, form-control boundary contrast (3:1), no horizontal
  scroll at 320px, no clipped text, and at-rest alignment of the Home grids.
- Placeholder and typed-text contrast, text selection, and the focus ring on
  every surface.
- Logo and canvas are painted from theme roles with no literal colours; the
  canvas repaints when the theme changes; the select arrow differs per theme and
  keeps 3:1; images are dimmed only in dark.
- Toggle: name, `aria-pressed`, top bar and menu copies stay in sync, Enter and
  Space, hidden without JavaScript, 44px at 1280 and 375, no layout shift on
  switch.
- Forced colours and print (below).

Dark found no contrast failures that the token pairings missed; the real dark
defects were hard-coded colours (logo, canvas, select arrow, photographs,
Turnstile theme) and they were fixed at the source.

## How the no-flash behaviour is tested (and what is not)

The risk is a page that paints in the wrong theme and then corrects itself. The
tests cover it from three sides:

- With a stored `dark` choice and a light system (and the reverse), a recorder
  installed before the page scripts shows `html[data-theme]` is already correct
  at `DOMContentLoaded` and was written exactly once, never corrected later.
- The page's resolved surface colour at load matches the chosen theme, not the
  system one.
- The head script sits before the stylesheet link in every generated page
  (static test on the rendered HTML), so the attribute exists before the first
  style calculation.

Not covered: a real first-paint capture was not taken, so the absence of a flash
is inferred from the checks above, not observed frame by frame. A person should
reload a few pages in dark on a real phone.

## Forced colours (Windows high contrast)

Checked with Chromium's `forced_colors: active` on Home, BizCheck and Contact, in
both themes at desktop width, plus the mobile menu row at 375px.

- The switch keeps a visible boundary: a 1px border in the system button text
  colour, and its icon is drawn in that same colour.
- Pressed state is told apart by shape, not colour: moon while off, sun while on.
  In forced colours the border also thickens (3px, no layout shift) while dark
  mode is on, so there are two cues that do not depend on colour.
- Keyboard focus shows an outline of at least 2px.
- In the mobile menu the row keeps its visible "Dark mode" text and a border.
- Tests: `test_toggle_is_visible_and_legible_in_forced_colours`,
  `test_toggle_focus_and_drawer_row_in_forced_colours`.

## Print

- Print always prints the light look, even when the screen is dark (explicit
  choice, a dark system with no choice, or no JavaScript at all). The generator
  re-declares the light roles inside `@media print`, after the dark rules, with
  selectors at least as specific as each of them.
- The switch is not printed; photographs are not dimmed.
- The earlier rule that shows every assembled element settled in print still
  holds. Tests: `test_print_always_prints_the_light_look_without_the_toggle`,
  `test_print_light_look_without_a_theme_attribute`.

## Turnstile widget (Contact and BizCheck)

Server verification, the action names, the site key and the script structure are
unchanged. Only the widget's `theme` option changed: it is chosen when the
widget renders, from the surface behind its container (`--surface` luminance),
because Cloudflare's `auto` follows the operating system and cannot see our
switch.

- Contact: the widget sits on the navy hero and renders dark in both themes.
- BizCheck: the widget sits on the form card, so it renders light in light and
  dark in dark.
- If the visitor flips the switch after the widget has rendered, it keeps its
  render-time theme until the next render or page load. It is not re-rendered on
  purpose: that would discard a token the visitor already earned.
- In the test browser third-party scripts are blocked, so the widget itself never
  loads. The behaviour is verified at the helper level: a stub widget records the
  options each page passes, in both themes
  (`test_turnstile_widget_theme_follows_the_surface_it_sits_on`). The live widget
  is a human check (below).

## Known limits

- Turnstile theme is fixed at render time (above).
- The logo and the canvases resolve to the same colours in both themes, because
  the top bar, hero and footer are navy in both. They are theme-driven, so they
  would change if those surfaces ever do; the tests assert the mechanism.
- `meta theme-color` is `#061325` (navy) in both themes, because the bar the
  browser tints to is navy in both. The script keeps separate light and dark
  entries ready to diverge. These meta values are the only colour literals left
  in the allowlist (browser chrome cannot use variables).
- Storage blocked or throwing (private modes, blocked site data): the page loads
  in the system theme, the switch still works for the visit, nothing is
  remembered, and no error is raised. Tested.
- The 56 light-only needs-review entries: these are the fixed top-bar links and
  logo, for which axe cannot resolve a background while cream page content
  scrolls beneath them. In dark that content is dark navy, so axe does not flag
  them. They are marked `theme: light` and measured from pixels in light. The
  suite fails if an entry without a theme is not needed in both, so these cannot
  silently go stale.
- Hover and transition states were checked by sampling, not exhaustively.

## Resolved after review

The Home "why" statistics are resolved: the owner chose "$24T" for the first
statistic and "50" for the second, with the extra hard-coded copy removed. Each
of the four statistics now renders a single numeral.

## What a person must still check

Not performed in this review:

1. A real screen reader (for example NVDA or VoiceOver) on the switch, in both
   the top bar and the mobile menu: the name is announced as "Dark mode" and the
   pressed state as on or off after activating it.
2. Real devices in dark mode: a phone and a tablet, in daylight and in a dark
   room; look for glare, banding and any text that looks too faint.
3. Real forced-colours and high-contrast settings (Windows contrast themes), not
   only browser emulation, on the switch and the menu.
4. The Turnstile widget on the live site, in light and dark, on Contact and
   BizCheck: it renders in the expected theme and a submission still succeeds.
5. A printed page or "Save as PDF" from a dark-mode browser: light look, no switch.
6. Reload several pages in dark on a real phone and watch for a light flash.
